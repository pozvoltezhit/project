# Deep Dive: фактический локальный стенд

Продолжительность 6:14. Реальные снимки интерфейсов и журналы, монтаж и локальная синтетическая озвучка.



## 00:00 — Архитектура закрытой платформы

Перед вами работающий учебный MVP платформы корпоративных знаний. Видео смонтировано из реальных экранов стенда и сохранённых журналов, озвучка синтезирована локально. Мы используем синтетические документы, чтобы проверить архитектуру и безопасность без данных предприятия. Control Plane принимает запрос и управляет состоянием LangGraph. Data Plane содержит канонические права и чанки в SQLite, векторный индекс Qdrant, граф Neo4j и локальную модель. Nginx публикует только loopback интерфейсы. Backend, базы и GPU подключены к внутренней сети без исходящего доступа. Облачных inference API в этой реализации нет.



## 00:41 — Ingestion и реальный OCR

Конвейер принимает текст и PDF. Если страница не содержит текстового слоя, локальный Tesseract распознаёт русский и английский текст. На экране именно image-only PDF, использованный в интеграционной проверке: насос Н-17, контур К-2 и датчик Д-8. Тест подтвердил распознанные идентификаторы, затем загрузил страницу и получил разрешённую цитату. При отсутствии OCR или недостаточном тексте загрузка завершается ошибкой. Документ получает hash, версию, tenant и grants. Чанки сохраняют номер страницы. Мы не утверждаем, что этот тест распознаёт геометрию чертежей или любые сложные таблицы.



## 01:22 — Neo4j: provenance и двухшаговый мост

Это реальный браузер Neo4j, подключённый к локальному контейнеру с административной аутентификацией. Выполненный Cypher показывает десять узлов и двенадцать связей. Document содержит Chunk, Chunk упоминает Entity. Три ребра CO_MENTION сохраняют источник и права. Насос Н-17 связан с контуром К-2 в первом документе, а контур с датчиком Д-8 во втором. Такой мост даёт двухшаговый GraphRAG. Совместное упоминание не доказывает физическую зависимость: утверждение подтверждается исходной цитатой. Канонический traversal выполняется в SQLite, Neo4j является производным зеркалом. Полный граф администратора не отдаётся обычным пользователям.



## 02:07 — User B: ответ из двух разрешённых источников

Пользователь B спрашивает, как связан насос с датчиком. Форма показывает режим vLLM и две короткие цитаты: насос подключён к контуру, контур контролируется датчиком. Есть название документа, страница и версия. Ни секретного бюджета, ни секретного ребра в выдаче нет. LangGraph последовательно проходит guard, planner, retrieval, graph expansion и reranking, но workflow нелинейный: при отсутствии evidence возможна одна ограниченная повторная попытка планирования. Модель выбирает цитаты из уже разрешённого контекста. Финальный validator проверяет точное вхождение текста и актуальные grants перед выдачей. Даже корректно сформированный ответ модели сам по себе не считается доверенным.



## 02:52 — RBAC: одинаковый вопрос, разные права

Теперь одинаковый вопрос о бюджете проекта П-9. Пользователь A с ролью restricted получает разрешённый синтетический источник. Пользователь B получает no evidence, сумма и граф секретного документа отсутствуют. Ключи на экране скрыты password полем, роли берутся из серверного provisioning файла, а не из тела запроса. Проверки отдельно подтвердили отказ чужой сессии, tenant isolation и запрет передачи роли через JSON. Отзыв grant во время генерации также блокирует выдачу. Общая сущность насоса не объединяет права соседних документов. Regex guardrails являются первым слоем; основная граница — ограниченные read-only инструменты и права на каждый source chunk.



## 03:42 — Jaeger: реальные стадии и локальная генерация

Открыт реальный Jaeger trace запроса к сервису knowledge platform. В нём тринадцать spans: guard, plan, retrieve, expand, rerank, generate и validate, а внутри генерации виден llm generate. Полная длительность этого конкретного запроса около одной целой шести десятых секунды. Это отдельный trace, а не средняя задержка теста. В telemetry не записываются вопросы, цитаты и секретный бюджет; остаются технические статусы и идентификаторы. Такая структура позволяет найти, где тратится время, и отличить задержку поиска от inference. История хранит ссылки на источники и повторно проверяет права, поэтому старый ответ не обходит отзыв доступа.



## 04:32 — vLLM: загрузка, AWQ Marlin и KV cache

На экране выдержка из сохранённого фактического журнала vLLM, а не имитация терминала. Qwen два с половиной, семь миллиардов параметров, подготовленная AWQ модель с проверенными hashes, загрузилась на RTX 4070. Marlin kernel использует около пяти целых двух десятых GiB для весов. Доступный KV cache около трёх целых тридцати пяти сотых GiB, контекст ограничен четырьмя тысячами девяноста шестью токенами, scheduler — четырьмя запросами. Первоначальный generic AWQ был медленным; сервер прямо рекомендовал совместимый Marlin. Мы сохранили baseline и повторили одинаковую нагрузку после переключения. Runtime использует только локальные weights, модель не обучалась и не скачивалась во время обслуживания.



## 05:22 — Grafana, нагрузка и границы результата

Grafana показывает реальные запросы, статусы, токены, очередь и KV utilization. Скорость на графике усредняется за пять минут, поэтому она отличается от короткого benchmark. В HTTP прогоне из двадцати четырёх запросов при concurrency четыре Marlin дал две целых двадцать семь сотых успешных запроса в секунду и p95 около одной целой девяноста шести сотых секунды, ошибок ноль. Generic AWQ дал ноль целых тридцать шесть сотых запроса в секунду и p95 одиннадцать целых шестьдесят шесть сотых секунды. Это тёплый одинаковый вопрос на трёх документах, не production capacity. CPU extractive замер отдельно помечен и не выдаётся за генерацию. До эксплуатации нужны доменный Golden Set, длительная нагрузка, SSO, mTLS, backup restore и проверка качества OCR.
