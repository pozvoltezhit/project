# Проверка функциональности

## Автоматические проверки

Установите requirements-lock.txt и requirements-dev.txt, затем выполните из корня проекта:

```powershell
python tools/verify.py
python -m backend.evaluate --output data/eval-report.json
```

verify.py запускает Ruff, Mypy, pytest с покрытием и backend.check. Результаты сохраняются в data/verification. GitHub Actions выполняет те же CPU-проверки в контейнере с изолированной временной БД. GPU-оценка выполняется отдельно с настроенным внутренним LLM_URL и аргументом --gpu для backend.evaluate.

Тесты покрывают: двухшаговую связь, RBAC и tenant isolation, shared entities, владельца сессии, отзыв прав во время генерации и перед сериализацией, masking PII, подозрительные документы, запрет внешнего inference URL, поддельные цитаты, смещения текста, отрицания и условия, token budget, версии индексов, резервное копирование, admission control и HTTP/SSE.

## Демонстрационные сценарии

1. Инициализируйте данные: `python -m backend.init_demo`.
2. Войдите с ключом engineer-b и спросите: «Как связан насос Н-17 с датчиком Д-8?». Проверьте два документа и provenance связей.
3. Спросите о секретном бюджете Н-17: engineer-b не должен получить закрытое значение. Повторите с engineer-a, имеющим роль restricted.
4. Откройте пользовательский /graph с тем же Bearer token и проверьте отсутствие закрытых связей.
5. В Jaeger найдите trace запроса и этапы агента; в Grafana проверьте HTTP latency и tokens, в локальном журнале vLLM - обработку генерации.

Корпус и наборы eval синтетические. Проверка инженерной достоверности на документах предприятия требует разметки профильными специалистами; автоматическая LLM-as-a-Judge оценка не реализована.
